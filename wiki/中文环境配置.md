# 中文环境配置

本文介绍如何在 Fedora + niri + DMS 中保留英文区域设置，并让用户应用优先显示中文。适合希望使用中文界面、同时保留英文默认格式的读者。启动与环境继承原理见[桌面启动流程](桌面启动流程.md)，基础术语见[部分概念](部分概念.md)。

**适用范围：** Fedora 常规 DNF 安装、systemd 用户服务和 Wayland 会话。安装命令不作为 Fedora Atomic 或其他发行版的通用步骤。所有终端示例按 Bash 编写；配置代码块是文件内容，不是终端命令。

## 目标与边界

推荐保留 `LANG=en_US.UTF-8`，为用户服务设置 `LANGUAGE=zh_CN:en_US`。这样支持相应翻译机制的程序会优先选择中文，缺少翻译时回退。

该方案通过 locale 变量和 systemd 用户环境配置实现。

- `LANGUAGE` 不只影响图形应用：继承它的终端程序也可能显示中文。
- 日期、数字等格式仍由相应 `LC_*` 类别或 `LANG` 决定。
- 应用必须有中文翻译，并支持相应语言选择机制；浏览器、Qt 应用和其他程序也可能有自己的设置。
- 登录界面属于另一用户环境，不会因普通用户的设置自动变成中文。
- 字体、中文输入法和界面翻译是不同事项。本文不配置 Fcitx5、Rime，也不重命名用户目录。

## 语言变量的含义

| 变量 | 作用 | 本文建议 |
| --- | --- | --- |
| `LANG` | 未单独设置的 locale 类别使用的默认值 | 保留 `en_US.UTF-8` |
| `LC_MESSAGES` | 程序消息的 locale 类别 | 没有特殊需求时不单独设置 |
| 其他 `LC_*` | 时间、数字、排序等类别 | 按需要单独设置 |
| `LC_ALL` | 覆盖所有 locale 类别 | 不长期写入全局配置 |
| `LANGUAGE` | GNU gettext 等机制使用的消息语言偏好列表 | `zh_CN:en_US` |

对 locale 类别而言，优先级是 `LC_ALL` → 对应的 `LC_*` → `LANG`。`LANGUAGE` 属于消息翻译机制，应另行理解，不能把它当成覆盖所有 locale 类别的变量。

GNU gettext 在适用时优先使用 `LANGUAGE`，但在 `C` locale 下忽略它；所以设置 `LC_ALL=C` 也会影响消息翻译。不同工具包的行为不保证一致。参见 GNU gettext 的[语言偏好说明](https://www.gnu.org/software/gettext/manual/html_node/The-LANGUAGE-variable.html)和[locale 变量说明](https://www.gnu.org/software/gettext/manual/html_node/Locale-Environment-Variables)。

## 配置前检查

在当前用户的终端执行：

```bash
localectl status
locale
locale -a | grep -E '^(en_US|zh_CN)'
rpm -q glibc-langpack-en glibc-langpack-zh langpacks-zh_CN
```

- `localectl status` 查看系统默认设置，不代表每个应用的当前环境。
- `locale` 查看当前终端进程的 locale，不能代替用户服务环境检查。
- `locale -a` 中的 `en_US.utf8`、`zh_CN.utf8` 是常见显示形式。
- 软件包查询报告未安装时，再考虑下一步安装。

同时检查用户环境目录中是否已有语言配置，避免新增多个文件反复覆盖：

```bash
grep -RnE '^[[:space:]]*(LANG|LANGUAGE|LC_[A-Z_]+)=' \
  "${XDG_CONFIG_HOME:-$HOME/.config}/environment.d"
```

目录不存在时会报告找不到目录，不代表系统故障。若自定义 `XDG_CONFIG_HOME`，应确保它在用户服务管理器启动环境中已经可用；仅在交互 Shell 中定义它可能导致编辑目录与实际读取目录不同。

## 安装语言支持

**权限：** 安装软件需要管理员认证。已安装时无需重复操作。

```bash
sudo dnf install glibc-langpack-en glibc-langpack-zh langpacks-zh_CN
```

前两个包提供相应 glibc locale 数据；`langpacks-zh_CN` 用于 Fedora 中文语言支持。具体应用可能还需要自身翻译资源，安装这些包不保证所有应用都变成中文。

安装后重新运行 `locale -a` 和软件包查询，确认所需 locale 可用。

## 保留系统默认英文

若 `localectl status` 已显示 `LANG=en_US.UTF-8`，跳过修改。若确实需要修改，先备份：

```bash
sudo cp -a /etc/locale.conf "/etc/locale.conf.backup-$(date +%Y%m%d-%H%M%S)"
```

然后执行：

```bash
sudo localectl set-locale LANG=en_US.UTF-8
localectl status
```

该操作修改系统默认语言。已有的 `LC_*` 设置仍需逐项检查，并保留符合使用需求的类别设置。

## 配置 niri 用户会话

### 备份并打开配置文件

优先修改已有的语言配置文件。以下以 `environment.d/locale.conf` 为例；若前面的检查发现使用了其他文件名，应编辑实际文件。

```bash
mkdir -p "${XDG_CONFIG_HOME:-$HOME/.config}/environment.d"
locale_file="${XDG_CONFIG_HOME:-$HOME/.config}/environment.d/locale.conf"
if [ -f "$locale_file" ]; then
    cp -a -- "$locale_file" "$locale_file.backup-$(date +%Y%m%d-%H%M%S)"
fi
vi "$locale_file"
```

### 合并语言偏好

下面是**合并片段**。替换已有 `LANGUAGE=`，保留其他需要的配置，不要重复追加同名项：

```ini
LANGUAGE=zh_CN:en_US
```

不要在这个文件中写 `export`、Shell 命令或 `source`。同一变量在多个环境文件中出现时可能被后读到的设置覆盖。

用户环境生成器会把这些设置提供给新启动的用户服务，继而影响 niri、DMS 及获得其环境的应用。会话脚本导入的登录环境也可能覆盖同名值，因此最终要检查运行环境。详见[环境变量传递原理](桌面启动流程.md#环境变量如何传递给应用)。

### 让新会话使用配置

保存工作后注销并重新登录，再检查下一节。若用户服务管理器因其他会话或 linger 继续存在，重新登录也可能保留旧环境；保存工作后重启系统能提供更明确的验证起点。

修改文件或重新打开终端后，已运行的 niri、DMS 和应用仍可能使用旧环境。应在重新进入会话后验证配置是否生效。

## 验证结果

### 检查用户服务环境

```bash
systemctl --user show-environment | grep -E '^(LANG|LANGUAGE|LC_[A-Z_]+)='
```

预期包含：

```text
LANG=en_US.UTF-8
LANGUAGE=zh_CN:en_US
```

同时检查是否有不符合预期的 `LC_ALL` 或 `LC_MESSAGES`。

### 检查 niri 与 DMS 进程

以下 Bash 命令只显示指定服务主进程的语言变量，不输出全部环境：

```bash
for unit in niri.service dms.service; do
    pid=$(systemctl --user show "$unit" -p MainPID --value)
    printf '%s\n' "$unit"
    if [ "${pid:-0}" -gt 0 ] && [ -r "/proc/$pid/environ" ]; then
        tr '\0' '\n' < "/proc/$pid/environ" | grep -E '^(LANG|LANGUAGE|LC_[A-Z_]+)='
    else
        printf '%s\n' '服务未运行或进程环境不可读。'
    fi
done
```

预期运行进程具有所需变量。`/proc` 检查主要反映启动环境，不是应用实际翻译选择的完整证明；DMS 的主进程检查也不能替代其界面子进程和应用的功能检查。

### 检查应用界面

从实际使用的启动器启动一个具有中文翻译的应用，检查菜单和设置页面。再从新终端检查 `locale`，确认日期、数字等类别仍符合预期。环境变量检查与应用界面检查应分别确认。

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| 用户服务环境没有 `LANGUAGE` | 文件位置、扩展名、其他同名设置，以及用户服务管理器是否仍沿用旧环境 |
| 服务环境正确，应用仍是英文 | 应用是否旧实例、启动途径、自带语言设置及翻译资源 |
| 图形应用中文，命令行也中文 | 这是环境继承的可能结果，不代表系统默认 `LANG` 被改成中文 |
| 中文显示为方框 | 检查字体，而不是反复修改 locale |
| 登录页面仍是英文 | 检查 Greeter 自身设置；当前用户文件不直接控制它 |
| 终端与启动器打开的应用语言不同 | 检查 Shell 配置及 D-Bus／用户服务启动路径 |

需要单次获得便于排错的英文命令输出时，可以使用：

```bash
env LC_ALL=C LANGUAGE=en_US locale
```

此处以 `locale` 为演示命令；实际使用时替换为需要运行的命令。该设置只影响这次命令及其子进程，且 `C` 会改变所有 locale 类别，不应据此永久设置整个桌面。

## KDE Plasma 与 GNOME 参考

以下说明供其他桌面环境参考，**尚未在本文的参考环境中验证**。应按所用桌面选择配置入口。

- **KDE Plasma：** 优先通过系统设置中的语言与区域相关页面分别设置语言和格式。若需直接编辑 `plasma-localerc` 中的 `[Translations]` 和 `LANGUAGE`，应先核对目标 Plasma 版本的配置格式与加载方式。
- **GNOME：** 通过设置中的“区域与语言”修改当前账户语言，注销后重新登录。登录屏幕语言需要单独设置。参见 [GNOME 官方说明](https://help.gnome.org/gnome-help/session-language.html)。

同一用户切换桌面时，已有 `environment.d` 仍可能影响用户服务，须检查是否与桌面自己的语言配置冲突。

## 恢复方法

1. 用户语言设置：恢复编辑前的备份，或只移除此次配置增加的 `LANGUAGE=`。如果该文件是此次配置新建且只包含这一项，可以删除该文件；保留其他用户配置。
2. 系统默认语言：仅在此次配置确实修改过时，按备份恢复 `/etc/locale.conf` 或使用 `localectl` 恢复原值。备份文件名以实际生成的时间戳为准。
3. 保存工作后注销并重新登录；仍有旧环境时重启，再重复验证。
4. 语言包可以保留，不为撤销一项用户语言偏好而批量卸载共享语言依赖。
